# UUID, 改名与玩家数据

## 身份验证与交给后端的 UUID 是两件事

`premiumUuid` 默认 `true`, 选择正版验证**之后**后端收到的 UUID, 不控制是否进行正版验证.

| 值 | 已验证 Java 连接的 UUID |
| --- | --- |
| `true` | Mojang UUID |
| `false` | 根据名字生成的离线 UUID |

此选项不会让未经验证的玩家获得正版身份. 使用代理时, 请在代理端配置.

## 修改 UUID 策略之前

1. 备份世界/玩家数据, 权限, 经济, 背包以及认证/FLP 数据库.
2. 记录代表性账号的两种 UUID, 检查各插件使用什么作为数据索引.
3. 在隔离副本测试. 背包变空常常是加载了另一个 UUID 的数据, 不一定是数据被删除.
4. 分别为每个受影响的插件安排迁移, 或保留原策略. FLP 不执行迁移.

不要在生产服随意切换 `premiumUuid`, 也不要未经检查复制其他服的配置. 代理网络中的后端应对转发身份有一致理解.

## 改名

`nameChangeCheck` 查询新名字, 可以按 Mojang UUID 找到并更新已有 FLP 记录. 它同步 FLP 的观察, 不会重命名所有插件账号或搬移世界数据.

Fabric/EasyAuth 路径可以在受支持的 SQLite 和账号一致性条件下, 按已验证 UUID 跟随已有正版账号. 不能覆盖已由另一个名字/身份持有的账号, 也不是适用于所有 EasyAuth 存储的通用改名迁移工具.

Bedrock/Floodgate 身份遵循自己的 UUID 和 linked 规则. 不要将 Java 正版 UUID 表套在 Bedrock 连接上, 也不要根据用户名前缀推导认证结论.
