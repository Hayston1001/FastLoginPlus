# 登录流程与身份信任

本文介绍 FLP 登录流程中主要模块的职责. 管理员操作请参阅[登录方式](accounts/login.md)和[绑定与切换](accounts/binding.md).

## 从连接到登录

1. FLP 根据名单和服务器策略选择登录方式. 正版 Java 登录需要验证当前连接; 查询到用户名或 UUID 不能证明玩家拥有账号.
2. 独立服由 FLP 配合数据包库完成验证. 代理部署中, 代理完成 Mojang 或 Floodgate 身份验证, 管理网络策略和 FLP 名单, 并向后端提供身份与策略.
3. 后端检查本地认证账号, 根据代理策略和账号状态决定注册, 登录, 要求密码或拒绝. 独立服在同一服务器上完成这些工作.
4. 只有认证插件确认账号动作成功, 才能认为玩家已登录. 名单更新和本地账号更新是不同操作, 失败时不能把其中一步当成全部成功.

已有密码账号需要持有人同意才能绑定正版. 已绑定的账号不能仅凭相同名字被其他连接打开. 具体能力会因认证插件和平台而异, 不应假设所有插件的提前登录行为相同.

## 信任边界

- 代理是网络中 FLP 名单和策略的来源; 后端认证插件管理自己的账号和密码. 后端不能用同名本地设置覆盖代理提供的有效策略.
- 后端必须验证来自代理的信息及其与当前连接的关联. 用户名, UUID 外形, 皮肤或插件消息通道名本身都不能证明身份.
- Velocity modern forwarding 需要正确配置密钥. Legacy forwarding 本身不能认证整个转发链. 两种方式都需要限制后端端口, 不能用代理 ID 白名单代替防火墙.
- 账号或身份读取失败时, 不能将失败当作账号不存在或允许访问. 已受保护的账号应保持认证锁或拒绝登录.

## Fabric 和 Bedrock

Fabric 后端使用 Velocity 转发的身份和策略, 结合 EasyAuth 账号完成本地认证. 密码账号绑定需要持有人先登录并同意, 再手动重连验证; 原密码保留.

Bedrock 支持范围取决于认证插件. Fabric/EasyAuth 当前只允许符合条件的未关联 Floodgate 玩家登录已有账号, 不自动创建 Bedrock 账号. 详见 [Bedrock 集成](integrations/bedrock.md).

代码入口和模块关系见[架构概览](development/architecture.md).
